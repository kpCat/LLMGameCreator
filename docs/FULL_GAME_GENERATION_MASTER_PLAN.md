# Full Game Generation Master Plan

Status: authoritative planning pack  
Scope: full game generation without graphics, music or sound production  
Non-scope: production code, WinForms UI, GamePackage schema, DB schema, Lua modules, runtime preview, provider calls

## 1. Product Goal

LLMGameCreator should become a game-generation machine that can take an approved game profile and produce a validated, playable, data-driven `GamePackage` without asking the user or Codex to invent the architecture again for every feature.

The product goal is not "one prompt writes a game". The goal is a controlled generation system:

```text
game intent
  -> game profile
  -> capability selection
  -> prompt context packs
  -> contract-bound artifacts
  -> validation and repair
  -> human approval
  -> GamePackage assembly
  -> runtime preview / export gates
```

The generated result must be inspectable, reproducible, repairable and exportable. The runtime must consume compiled game data, not model output.

## 2. What "Full Game Generation" Means In This Project

"Full game generation" means the editor can generate all non-media game data needed for a coherent playable game slice or whole game family:

- game profile, genre, tone, camera/runtime target and core loop;
- world scale, finite maps, regions, chunks and infinite-world generator rules;
- tile/biome/region/landmark/road/reachability data;
- entity prototypes, entity instances, NPC archetypes, schedules and factions;
- dialogue graphs, dialogue-combat records, quests, objectives and stages;
- items, inventories, equipment, loot, economy, vendors and crafting;
- stats, formulas, progression, abilities, statuses and combat definitions;
- automation, city-builder and simulation configuration when selected;
- UI IR/HUD records for a future player/export layer;
- validation, repair, approval, assembly and export artifacts.

It does not mean the system generates final images, music, sounds, Unity scenes or arbitrary runtime code in this task family. Media may be represented by requests, asset ids and fallback contracts, but media production is outside this plan.

## 3. Explicit Non-Goals

This master plan does not authorize:

- LLM as runtime authority;
- LLM writing C#, executable Lua, Unity code or database migrations;
- Lua mutating C# runtime state directly;
- direct GamePackage mutation from unapproved artifacts;
- huge tile-array dumps for infinite worlds;
- hidden provider calls;
- schema changes without a migration plan;
- new UI without service and validation seams;
- one-off pipeline layers that do not improve user-visible generation quality.

Required consistency assertions for future tasks:

- LLM is not runtime authority.
- Lua is deterministic and sandboxed.
- C# owns validation, promotion, export and runtime.
- Infinite worlds are generated by rules, seeds and chunks, not massive precomputed tile dumps.
- GamePackage schema is not changed by this task.
- Current one-click export is acknowledged as a narrow vertical MVP, not the full generator.

## 4. Current State Summary

Current strengths:

- `GamePackage` is the playable source of truth.
- Validation already protects package, script, asset, economy, encounter and narrative contracts.
- Design DB stores editor-side knowledge, generator plans, generated artifacts and validation results.
- Generator Plan preview, draft execution, queue, deterministic production, approval, GamePackage assembly and one-click export exist as a narrow vertical slice.
- Prototype Lua can create strict `game_package_patch_v1` artifacts through controlled declarations.
- Runtime services execute headless data-driven gameplay systems without LLM calls.

Current limitation:

The one-click export flow is a narrow vertical MVP. It proves the artifact-to-package chain, but it does not yet represent a full generator. It emits deterministic draft content from templates and selected example context. It does not yet use Lua as the main generator runtime, does not call an LLM provider, does not execute real module batches, and does not cover every capability domain listed in this plan.

## 5. Target Architecture

The target architecture is:

```text
Design knowledge
  -> Game profile
  -> Capability matrix / feature bundles
  -> GeneratorPlan
  -> Prompt context pack
  -> LLM draft artifacts and/or Lua deterministic IR
  -> Artifact contract validation
  -> Repair loop
  -> Human approval
  -> GamePackage assembly
  -> Runtime preview validation
  -> Export profile / future Unity IR
```

Stable ownership:

- C# owns authority, validation, storage, promotion, assembly, export, runtime and audit.
- LLM owns draft text and contract-bound JSON proposals only.
- Lua owns deterministic module generation and IR/config/data only inside a sandbox.
- GamePackage owns final playable content.
- Runtime owns mutable gameplay state; package definitions are not runtime state.

## 6. C# / LLM / Lua Responsibility Split

Mandatory statements:

- LLM never writes executable runtime code.
- LLM outputs contract-bound JSON drafts.
- Lua modules may generate deterministic IR/config/data, but only inside sandbox and only through manifest-declared contracts.
- C# validates, stores, promotes, assembles, exports, simulates and owns final authority.
- A model saying "valid" is never a validation result.
- A Lua module returning data is never promotion by itself.
- Human approval is required for canon, capability, profile and final promotion decisions.

## 7. Game Generation Lifecycle

Lifecycle states:

```text
profile_draft
profile_approved
capability_selection_draft
generator_plan_draft
generator_plan_approved
artifact_generation_running
artifact_validation_failed
artifact_repairing
artifact_ready_for_review
artifact_approved
package_assembly_ready
package_assembly_validated
runtime_preview_validated
export_ready
```

Every lifecycle transition must leave an artifact, validation record or human decision. No hidden state transition should happen because a prompt "looked good".

## 8. Supported Game Families / Genres

The platform should be able to grow toward these families without rewriting the architecture:

- party RPG / dungeon crawler;
- narrative political RPG;
- visual novel / dialogue RPG;
- tactical RPG;
- survival sandbox;
- roguelike;
- automation / Factorio-like;
- city-builder / colony simulation;
- open-world or region-based RPG;
- alien or non-human perception games.

Each family is a capability bundle, not a hardcoded mode. New families are added by capability entries, artifact contracts, Lua modules, validators and preview/export support.

## 8.1 Presentation / Form-Factor Strategy

A full generator must not be limited to top-down 2D adventures. Game profiles must select explicit taxonomy ids before prompt, artifact, validator, runtime preview or export planning begins.

Required profile choices include:

- presentation mode, such as `presentation_mode/top_down_2d`, `presentation_mode/tactical_grid_2d`, `presentation_mode/first_person_grid_2d_textures` or `presentation_mode/map_and_panel_rpg`;
- world topology, such as `world_topology/region_graph`, `world_topology/seamless_chunks`, `world_topology/infinite_chunks` or `world_topology/first_person_grid_dungeon`;
- actor model, such as `actor_model/single_player_character`, `actor_model/party_blob`, `actor_model/party_individuals` or `actor_model/colony_population`;
- inventory, combat, progression, pathfinding and NPC behavior model ids.

The authoritative reference docs are:

- `docs/GAME_FORM_FACTORS_AND_PRESENTATION_MODES.md`;
- `docs/GAME_SYSTEM_VARIANT_TAXONOMY.md`.

## 8.2 Pseudo-3D / 2D Asset 3D-Like Rendering Target

Pseudo-3D from 2D assets is a first-class future presentation mode.

Required assertion:

```text
presentation_mode/first_person_grid_2d_textures
actor_model/party_blob
world_topology/first_person_grid_dungeon
combat_model/blobber_party_turn_based
pathfinding/first_person_grid_movement
```

This target uses data contracts and refs. It does not require 3D model generation. Wall, floor and ceiling texture refs may be 2D; actors/items/projectiles may be billboards or sprites; runtime/export layers may render a 3D-like view from 2D package data.

GamePackage should store data, contracts and refs, not Unity scene/model objects.

## 9. Infinite / Chunked World Support Strategy

Infinite worlds must be generated by rules, seeds and chunk contracts.

Required approach:

- store world-scale policy and chunk generator config;
- store seed, chunk size, biome rules, sparse overrides and landmark rules;
- validate local chunk reachability and cross-chunk constraints;
- persist mutable chunk deltas in runtime/save state, not package definitions;
- avoid huge precomputed tile arrays except for small finite maps.

Blocked approach:

- asking the LLM to print an entire continent as raw tiles;
- storing millions of generated cells in `package.json`;
- accepting a chunk generator without deterministic seed/config and validation gates.

## 10. Data-Driven Runtime Strategy

Runtime consumes data:

- maps, chunks, tile prototypes and entity prototypes;
- interactions, requirements, costs and outputs;
- quests, dialogue, factions and reputation;
- stats, resources, abilities, statuses and encounters;
- inventory, equipment, loot, transactions and crafting;
- generator-config outputs that have been compiled into package data or runtime lookup data.

Runtime does not consume:

- raw LLM prompts;
- unapproved generated artifacts;
- arbitrary Lua source;
- provider-specific generation requests;
- WinForms editor state.

## 11. Artifact Contract Strategy

Every generation output must name a contract. Initial required contracts include:

- `game_profile_v1`;
- `semantic_pack_v1`;
- `scene_pack_v1`;
- `entity_pack_v1`;
- `quest_pack_v1`;
- `mechanics_pack_v1`;
- future `dialogue_pack_v1`, `world_chunk_config_v1`, `npc_schedule_pack_v1`, `combat_pack_v1`, `economy_pack_v1`, `ui_ir_v1`, `unity_ir_v1`.

Each contract must define:

- schema version;
- producer role;
- allowed inputs;
- required ids and enums;
- validation gates;
- repair policy;
- promotion target;
- non-goals.

## 12. Validation / Repair / Approval Strategy

Validation layers:

```text
syntax -> schema -> id/enum/reference -> capability dependency -> semantic consistency -> package validation -> runtime smoke -> export dry-run
```

Repair is allowed only for repairable failures:

- invalid JSON;
- missing required field;
- enum/id drift;
- local reference mismatch;
- bounded semantic issue.

Repair is not allowed to redesign the game, change approved canon, silently enable content overlays or bypass validators.

Approval gates:

- profile and feature bundles require human approval;
- new capability domains require human approval;
- generated artifacts require artifact review before promotion;
- package assembly/export requires deterministic validation.

## 13. Prompt Hardening Strategy

Every prompt must include:

- model role;
- artifact contract;
- allowed input context;
- exact output schema;
- immutable ids/enums;
- validation gates;
- repair policy;
- forbidden outputs.

Strict JSON artifact prompts must return exactly one JSON object, no markdown fences, no explanations, no translated machine ids and no hidden contract mixing.

## 14. Lua Module Integration Strategy

Lua is a deterministic generator/IR layer, not a trusted runtime authority.

Lua modules must:

- be sandboxed;
- avoid `io`, `os`, `debug`, `package`, `load`, `loadfile`, `dofile`, networking and filesystem access;
- return JSON-serializable data;
- declare manifest, input schema, output schema, config schema and capabilities;
- return diagnostics instead of throwing for normal validation failures;
- produce compact rules, configs, sparse overrides or IR, not huge content dumps.

Current one-click export does not yet use Lua as the main generator runtime. Lua integration must be introduced as a reviewed milestone with sandbox, manifest, validation, artifact contracts and tests.

## 15. GamePackage Assembly Strategy

GamePackage assembly must remain deterministic:

- read approved artifact sets;
- map known artifact kinds to existing package fields;
- preserve unmapped artifacts as diagnostics until a schema or compiler exists;
- run `GamePackageValidator`;
- export only through existing package repository paths;
- never mutate a current package unless an explicit apply/export request says so.

Assembly should grow by adding contract mappers and validators, not by letting arbitrary artifacts write package JSON.

## 16. Runtime Preview Strategy

Runtime preview is a validation tool, not the final player.

Required use:

- load assembled package;
- execute deterministic smoke commands;
- verify state serialization where relevant;
- report missing refs, blocked moves, impossible interactions and invalid dialogue/quest/combat flows.

Non-goals:

- final UX polish;
- media playback completeness;
- direct model or provider calls;
- hidden package repair.

## 17. Extensibility Strategy

New genres and mechanics must be added by:

1. capability matrix entry;
2. artifact contract;
3. prompt family or Lua module manifest;
4. validator;
5. package assembly mapping or explicit blocked status;
6. runtime preview/export gate if playable;
7. focused tests and docs.

Do not add a feature as only UI, only prompt text or only Lua source.

## 18. Performance And Context-Budget Strategy

The system must not scale by sending everything to the model.

Rules:

- select context by contract, capability, profile and validation target;
- summarize old outputs into approved knowledge artifacts;
- shard generation into small artifacts;
- repair only the failing artifact;
- use seeds/configs/rules for large worlds;
- keep runtime lookup data compiled or indexed;
- run validator/smoke checks before user review whenever possible.

## 19. Milestones From Current State To Full Generator

- M0: current vertical slice baseline documented and treated as narrow MVP.
- M1: authoritative planning pack, capability matrix and role contract.
- M1.1: game form factor and system variant taxonomy.
- M2: artifact review/approval UI made capable of reviewing many artifact types.
- M3: capability and feature bundle picker.
- M4: strict LLM artifact generation and repair loop.
- M5: Lua module registry/executor integration through sandbox and manifests.
- M6: rich GamePackage assembly for world/entities/dialogue/quests/items/combat/economy.
- M7: infinite/chunked world generation through config and seed contracts.
- M8: runtime preview validation loop across generated systems.
- M9: full game template families and balancing validators.
- M10: export profiles and future Unity IR.

## 20. Definition Of Done For "Full Generator Without Media"

The system can be called "full generator without media" only when:

- at least three distinct game families can be generated through the same lifecycle;
- selected capabilities produce contract-bound artifacts;
- LLM and Lua outputs are validated before approval;
- package assembly covers world, entities, quests, dialogue, items/economy and combat where selected;
- finite and chunked/infinite world paths are both supported;
- runtime preview can smoke generated packages;
- failed validation produces repairable diagnostics;
- human approval and audit artifacts exist for promotions;
- one-click export is no longer only a narrow deterministic template slice;
- no runtime path depends on LLM, provider calls or unapproved generated code.
