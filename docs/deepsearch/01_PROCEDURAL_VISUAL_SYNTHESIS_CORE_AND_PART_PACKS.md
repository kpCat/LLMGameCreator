# Исследование Procedural Visual Synthesis Core для LLMGameCreator

## Executive summary

Для вашего проекта оптимальная линия — не “генерация картинок”, а **компиляция визуалов из компактных part packs**: небольших повторно используемых деталей, масок, палитр, сокетов, правил совместимости и сидов. Это лучше всего совпадает с уже зафиксированными принципами LLMGameCreator: source of truth должен оставаться в GamePackage/manifest/catalog/recipes; Runtime и Unity Player не должны выполнять вызовы LLM, медиа-провайдеров или сетевых генераторов; editor-side pipeline должен работать через детерминированные правила, quarantine/review и safe fallbacks. В текущих проектных документах это уже прямо задано как направление для visual rule stack, detail generator core, part-pack compiler, provenance/review и Unity-consumption только для approved asset refs. citeturn41view1turn41view3

С инженерной точки зрения вам нужен **трёхслойный стек**. Первый слой — чистое domain/core-моделирование: part pack IR, recipe IR, validation, hashing, provenance, review-state, deterministic selection. Второй слой — optional editor adapters: rasterizer, atlas packer, Aseprite/Tiled/LDtk importers, WinForms preview. Третий слой — Unity consumption adapters, которые импортируют уже материализованные PNG/atlas/metadata и, при необходимости, перекладывают их в Sprite Atlas или prefabs, но не “думают” и не генерируют заново. Такой split также соответствует рекомендациям Unity: Unity поддерживает .NET Standard 2.1 и .NET Framework compatibility levels, но не поддерживает .NET Core assemblies как managed plug-ins; кроме того, Unity отдельно предупреждает про риски сторонних библиотек и прямо не гарантирует поддержку `System.Drawing`. citeturn31view0turn30view0

Главный практический вывод: **в core не надо тащить внешний raster stack**. В core нужны только контракты, выбор вариантов, seed-driven deterministic ordering, валидация и canonical hashing. Любые ImageSharp/SkiaSharp/Aseprite/Tiled/LDtk/atlas packer должны жить за adapter boundary. Это позволит удержать ядро независимым от лицензий, платформенных ограничений и Unity-совместимости, а также не нарушит ваше требование не добавлять внешние зависимости в core без optional adapter boundary. Поддерживающие инструменты для этого подхода уже существуют: Aseprite умеет экспортировать слои, теги, slices и pivots в JSON; Tiled и LDtk умеют хранить typed metadata и rule-driven data; Unity умеет эффективно потреблять готовые atlas assets, но его `Texture2D.PackTextures` меняет формат/мипмапы и даже может масштабировать входные текстуры, поэтому это плохой “источник истины” для вашего authoring pipeline. citeturn33view1turn33view0turn34view0turn34view1turn35view0turn32view0turn32view1

## Рекомендуемая архитектура synthesis core

Правильная базовая модель — это не “ассет = картинка”, а **ассет = сборочная спецификация**. Здесь полезно разделить сущности на `PartPack`, `PartVariant`, `SocketMap`, `PaletteProfile`, `MaskSet`, `OverlaySet`, `AssemblyRecipe`, `MaterializationJob` и `MaterializedArtifact`. Такой подход близок к тому, как зрелые data-driven инструменты разделяют definitions и instances: LDtk в JSON отделяет `defs` от `levels`; Tiled отделяет tilesets/templates от размещения на карте; в ваших внутренних документах такой же разрез уже обозначен для visual rule stack, sidecar contracts и approved asset bindings. citeturn35view2turn34view2turn34view4turn41view1

На практике `PartPack` должен быть **стилевым контейнером**, а не просто папкой PNG. Внутри него должны жить: семейства силуэтов, базовые детали, допустимые overlay-слои, palette slots, material roles, anchors/pivots, masks для реколора/наложений, а также compatibility rules. Художественная согласованность в такой системе достигается не “умностью” генератора, а строгим ограничением комбинаторики: один silhouette family, фиксированная система z-order, ограниченные palette families, проверяемые sockets, review-approved overlays и запрет на смешение несовместимых part families. Это подтверждается внешними примерами: LPC generator строится на общем стиле и жёстком учёте attribution/licensing по выбранным частям, а Aavegotchi generator использует configuration-driven trait-to-layer mapping и batch composition на базе JSON-конфигурации. citeturn17view0turn17view1

Я бы рекомендовал следующую логическую сборку кадра или иконки: `base silhouette` → `surface/base fill` → `species/material markings` → `equipment/clothing` → `state overlays` → `lighting/outline normalization` → `presentation transforms`. Для существ это хорошо совпадает с уже описанным у вас layer stack уровнем visual genome: тело, поверхности, маркеры, выражение, appendages, одежда, броня, аксессуары, раны/грязь, трансформации и rating-gated overlays. Для предметов и иконок тот же принцип работает через “раму предмета”: shape, material fill, trims, insets, damage/wear, glow, faction mark, rarity mark. citeturn41view3

Сокеты и pivots должны быть **первоклассными данными**, а не побочным соглашением художников. Aseprite здесь особенно полезен как входной authoring-инструмент: slices поддерживают bounds, 9-slice center и explicit pivot; эти данные экспортируются в sprite-sheet JSON, а CLI умеет выдавать layers, tags и slices в `meta`. Это означает, что для artist-authored part packs можно использовать `.aseprite`/`.ase` как исходник, затем в editor pipeline извлекать из него `anchorMap`, `pivot`, `sliceBounds`, `frameTags` и layer names. Для tile-oriented мира Tiled даёт object alignment, drawing offset, typed properties, inheritance и templates, а LDtk даёт IntGrid/auto-layer модель для rule-based tile placement. citeturn33view0turn33view1turn34view4turn34view0turn34view2turn35view1turn35view0

Отдельно важно, что editor-side preview должен работать в двух режимах. Первый — **ephemeral preview**, где вы быстро собираете итог из parts + palette + seed без записи в GamePackage. Второй — **materialization**, где вы сохраняете уже проверяемый результат: PNG/atlas, JSON-sidecar, hashes, recipe fingerprint, review state, fallback binding. Это снова напрямую совпадает с вашим roadmap: сначала metadata/validator/fixture focus, затем deterministic preview metadata, затем sidecar proof, provenance, quarantine и promotion. citeturn41view1

## IR и sidecar contracts

Минимальный рабочий IR я бы строил как четыре контракта.

`visual.partpack.json` — контракт набора деталей. В нём должны быть `packId`, `packVersion`, `styleProfileId`, `projectionModes`, `paletteFamilies`, `partFamilies`, `socketSchema`, `overlaySchema`, `license/provenance hints`, `reviewState`, `contentHash`. Часть `partFamilies` должна описывать не только файл, но и semantic role: например `body.base.humanoid`, `head.hair.short`, `armor.shoulder.light`, `terrain.edge.coast`, `building.facade.wood.small`. Такая модель лучше масштабируется на 100+ существ и на мирные объекты, чем flat-список картинок. Поддержка custom properties, typed classes и tile property inheritance в Tiled, а также defs/entities/enums/fields в LDtk показывает, что метаданные нужно делать структурными, а не stringly-typed. citeturn34view0turn35view2turn35view3

`visual.recipe.json` — контракт сборки. Здесь должны жить `recipeId`, `domainProfile`, `recipeVersion`, `styleProfileId`, `assemblyGraph`, `selectionRules`, `stateAxes`, `paletteBindings`, `maskBindings`, `seedPolicy`, `fallbackPolicy`. Именно recipe должен определять, какие slot families допустимы и как seed влияет на выбор. В вашем roadmap уже закреплён подход, где visual rule stack потребляет domain/biome/culture/role/state/seed и резолвит deterministic visual recipes editor-side, не делая их authoritative runtime state и не раздувая public GamePackage schema раньше времени. citeturn41view1

`visual.materialized.json` — sidecar результата. Он должен включать `artifactId`, `artifactKind` (single PNG, sprite sheet, atlas, mask set, icon sheet), `sourceRecipeId`, `packDigests`, `inputSeed`, `rendererAdapter`, `rendererVersion`, `outputFiles`, `byteHashes`, `pixelSize`, `sliceMap`, `spriteRects`, `pivotMap`, `approvedAssetRef`, `safeFallbackRef`, `exportPolicy`, `reviewStatus`. На этой стадии полезно сразу держать data model таким образом, чтобы Unity могла читать только этот sidecar плюс approved files. Это согласуется с вашим Stage 5/10: sidecar contracts для textures/facades/billboards/pivots/scale/sorting/collision/fallbacks и Unity/Player consumption только approved refs и deterministic fallbacks. citeturn41view1

`visual.review.json` — контракт human review/provenance. Здесь нужны `candidateQuarantine`, `reviewDecision`, `reviewedBy`, `reviewTimestamp`, `rating`, `adultEnabled`, `safeFallbackRequired`, `sourceRecipeId`, `relativePathFacts`, `hashFacts`, `tamperCheck`, `promotionDecision`. Это уже почти напрямую повторяет ваши требования Stage 1, 6, 7, 8 и 9: provenance, rating metadata, approvedAssetRef, hash facts, quarantine, export policy, failure-closed safe fallback и WinForms review workspace. Для adult-capable направлений хранить надо только политику и gating metadata, а не runtime generation или prompt recipes. citeturn41view1turn41view3

Практически я бы не делал part packs публичной частью GamePackage на первом шаге. Лучше держать их в **editor-owned sidecar namespace** и поднимать в основной package только после доказанной необходимости у consumer-слоя. Это полностью соответствует вашим внутренним правилам: “keep recipes sidecar/editor-owned until a package binding goal is selected” и “no public GamePackage schema mutation without dedicated consumer proof”. citeturn41view1

## Детерминированный cache, materialization и provenance

Для такого проекта кэш должен быть **content-addressed и двухуровневый**. Первый уровень — быстрый preview cache по ключу вроде `renderer + recipe canonical json + partpack digest set + seed + palette binding + adapter version`. Второй уровень — promotion/materialization cache, где артефакт получает стабильный `artifactId`, сохраняет байтовый хэш и становится объектом review. Хэширование лучше разделить по задаче: для provenance и tamper detection использовать встроенный `.NET` `SHA256`; для быстрых технических cache keys можно дополнительно использовать `XxHash128` из официального `System.IO.Hashing`, если действительно понадобится ускорение на больших пакетах. citeturn29search0turn29search2turn29search1turn29search13

Ключевая деталь: **кэш надо считать по канонизированным данным, а не по файловым путям**. Путь может поменяться, а рецепт — нет. Поэтому в canonical form должны входить: нормализованный JSON recipe, нормализованный список входных part digests, seed, palette/material profile, renderer adapter id/version, target projection mode, optional platform import profile. Если меняется хотя бы один из этих параметров — артефакт инвалидируется. Это особенно важно для reviewed/provenance pipeline, потому что ваши документы уже требуют reject по tampered hash, missing file, fake success и unreviewed promotion. citeturn41view1

Отдельно важно не полагаться на Unity runtime packing как на источник кэша. `Texture2D.PackTextures` прямо документирован так, что может менять размер, формат и mipmaps входных текстур, а если всё не помещается в `maximumAtlasSize`, то входные текстуры масштабируются вниз, чтобы влезть. Для ваших целей это означает риск потерять детерминизм authoring-result и несоответствие reviewed pixel output тому, что видит Unity. Поэтому в editor materialization pipeline лучше делать собственный pack step или внешний deterministic packer, а Unity Sprite Atlas использовать уже как downstream consumption/optimization stage. citeturn32view0turn32view1

Для provenance стоит хранить не только hash файла, но и **цепочку происхождения**: `sourceRecipeId`, `sourcePackIds`, `sourcePackDigests`, `baseVariantIds`, `stateAxes`, `seed`, `rendererVersion`, `reviewStatus`, `exportPolicy`, `safeFallbackRef`. Для artist-authored packs добавляйте также `authoringSource` и `sourceTool` — например, Aseprite slice/layer export или Tiled template. Это особенно полезно из-за лицензирования и credit provenance: LPC generator показывает, что attribution может зависеть от конкретно выбранных частей, а не от “пака в целом”. citeturn17view0

Расположение на диске я бы развёл так: `cache/preview/`, `cache/materialized/`, `review/quarantine/`, `review/promoted/`. Preview может уничтожаться автоматически. Materialized — переиспользуется until invalidated. Quarantine — immutable и с обязательными hashes. Promoted — только по review decision. Это лучше всего соответствует вашему staged pipeline: candidate quarantine, promotion decision, safe fallback generation и Unity consumption only of approved refs. citeturn41view1

## Candidate libraries и инструменты

**SkiaSharp** — сильный кандидат для editor-preview adapter и, возможно, для PNG/materialization adapter. Официально это cross-platform 2D graphics API for .NET на базе Skia; лицензия фактически MIT; есть актуальный stable release `4.148.0` от 22 июня 2026 года; для WinForms есть `SKControl` в `SkiaSharp.Views.WindowsForms`. Сильные стороны: быстрый рендер, хороший текст/вектор/композиция, зрелая экосистема, удобство для WinForms preview. Риски: это bindings к нативному движку Skia, поэтому это дополнительная operational complexity по сравнению с полностью managed-стеком; в core встраивать нельзя, только через optional adapter. Вердикт: **нужно прототипировать как основной preview adapter**. citeturn20search13turn38view1turn37view3turn26search0turn26search5

**ImageSharp** — сильный кандидат для headless materialization adapter, особенно если вам важнее чисто managed pipeline и отсутствие графического UI. Официально это high-performance fully managed cross-platform image library for .NET, в текущей линии built against .NET 8; проект активен, release `v4.0.0` вышел 12 мая 2026 года. Главный риск — лицензия: Six Labors Split License, бесплатное использование покрывает open source, transitive dependency, non-profit и direct dependency для for-profit ниже $1M gross revenue; выше этого порога нужен commercial license. Поэтому ImageSharp нельзя “бездумно” класть в core и нельзя принимать как default без осознанной лицензионной проверки. Вердикт: **нужно прототипировать как optional headless raster adapter, но не делать dependency ядра по умолчанию**. citeturn37view0turn37view1turn39view0turn19search19

**System.Drawing.Common** — не подходит для shared/core и вообще плохой выбор для Unity-ориентированного пайплайна. Microsoft прямо отмечает, что пакет теперь Windows-specific, а на не-Windows платформах в .NET 6+ возникают ограничения/исключения; Microsoft рекомендует мигрировать на SkiaSharp или ImageSharp. Unity отдельно пишет, что `System.Drawing` не поддерживается и не гарантируется на всех платформах. Для чисто локального WinForms utility на Windows использовать можно, но это создаст ложное чувство “простоты” и сломает переносимость архитектуры. Вердикт: **не подходит для core и для Unity-shared кода; максимум — временный локальный dev utility вне общей архитектуры**. citeturn30view0turn31view0

**Aseprite** — очень хороший artist-side источник для part packs, особенно для pixel-art, small reusable parts, slices, tags, tilemaps и palette-oriented authoring. Официальный CLI умеет экспортировать spritesheet + JSON, список layers/tags/slices, а slices содержат bounds/center/pivot; с v1.3 есть tilemap layers и tilesets. Это делает Aseprite отличным upstream authoring tool для входных `.aseprite`/`.ase` источников, из которых editor pipeline вытаскивает `pivot`, `anchors`, `frameTags`, `layer groups`, `slice bounds`. Однако лицензия самого приложения после 2016 года — не GPL, а EULA/source-available: официальный пакет нельзя перераспространять третьим лицам. Значит, Aseprite надо считать **внешним авторским инструментом**, а не встраиваемой зависимостью или redistributable частью продукта. Вердикт: **можно внедрять сейчас как optional import source, но только как external tool boundary**. citeturn33view1turn33view0turn33view2turn15search1turn15search4

**Tiled** — хороший инструмент для world grammar, tile/object metadata и templates, но не source of truth для synthesis core. У него сильные стороны: typed custom properties, custom classes/enums, tile property inheritance, templates, terrain/Wang sets, external tilesets, object alignment и drawing offset. Это делает Tiled хорошим **bridge-format authoring layer** для мира, интерактивных объектов и правил соседства. Но у самого редактора смешанный licensing footprint на репозитории, и встраивать его как core dependency смысла нет; кроме того, ваш проект явно хочет держать source of truth в GamePackage/recipes, а не в редакторских форматах. Вердикт: **нужно прототипировать как importer/exporter adapter, но не как корневой контракт системы**. citeturn10view0turn34view0turn34view1turn34view2turn34view4

**LDtk** — хороший соседний инструмент для data-driven world authoring и rules over IntGrid, а не для part-pack core. Он MIT-лицензирован, хранит данные в чистом JSON, чётко разделяет `defs` и `levels`, поддерживает IntGrid, custom fields, entities и auto-layers/rules. Сам редактор не получал новый stable release после января 2024 года, но экосистема жива, а Unity importer `LDtkToUnity` активно развивается и выпустил `6.12.3` в апреле 2026 года. Это хороший знак для editor bridge. Вердикт: **прототипировать для world/biome/domain authoring, но не использовать как authoritative visual synthesis IR**. citeturn12view0turn35view2turn35view1turn35view0turn36view1

**RectpackSharp** — лёгкий и прагматичный кандидат для atlas packing за adapter boundary. Это маленькая C# библиотека для .NET Standard, MIT, latest release 1.2.0 от 9 января 2024 года, рассчитанная именно на rectangle packing и texture atlas/sprite sheet use cases. Плюс в том, что библиотека небольшая и при желании может быть даже vendored в adapter-проект. Минус — проект небольшой и не такой зрелый, как, например, сам Unity Sprite Atlas; поэтому делать его “архитектурным центром” не стоит. Вердикт: **можно внедрять сейчас как optional atlas-packing adapter или как reference implementation**. citeturn28view0

**Free Texture Packer** — полезный референс и внешний одноразовый инструмент, но не хорошая core/current dependency. Он MIT, умеет trimming, rotation, multipacking и custom export templates, однако сам автор прямо пишет, что больше не имеет времени на развитие и будут исправляться только критические баги; latest release у desktop-тулзы датирован 2021 годом. Для production-authoring chain это слишком слабая траектория сопровождения. Вердикт: **отложить; можно использовать только как reference exporter или временный external utility**. citeturn27view0turn27view1

**SuperTiled2Unity и LDtkToUnity** — хорошие downstream importers для Unity, но не более того. Оба решения используют Unity Scripted Importers; SuperTiled2Unity MIT и импортирует Tiled maps прямо в Unity, LDtkToUnity MIT и активно развивается, умеет поля/entities/enums и может паковать tileset output в SpriteAtlas. Это полезно именно как consumer-side integration, когда source of truth уже сформирован editor pipeline или sidecar manifests. Вердикт: **можно подключать позже как optional Unity adapters, когда будут стабилизированы ваши sidecar contracts**. citeturn36view0turn36view1

## Что Codex должен делать сейчас

**Можно внедрять сейчас.** Сразу стоит делать чистый `ProceduralVisual.Core`, в котором нет никаких графических библиотек. Внутри него должны появиться: canonical IR для `PartPack`, `Recipe`, `Socket`, `PaletteProfile`, `MaskSet`, `OverlaySet`, `MaterializedArtifact`; deterministic selector по seed; canonical JSON serialization; SHA-256 based provenance; validator rules для safe fallback, export policy, review status и approved/promoted separation. Это напрямую соответствует вашей текущей проектной дорожной карте и не конфликтует ни с Unity, ни с лицензиями внешних тулов. citeturn41view1turn29search0

**Нужно прототипировать.** Параллельно стоит сделать два editor adapter-проекта: `ProceduralVisual.Adapter.SkiaSharp` для WinForms preview и `ProceduralVisual.Adapter.ImageSharp` либо `ProceduralVisual.Adapter.SkiaSharp` для headless materialization/PNG output. На уровне прототипа достаточно уметь: собрать 5–20 слоёв в итоговую bitmap, применить palette slots через masks, посчитать pivots/sockets, отдать preview PNG и `visual.materialized.json`. После этого вы сможете сравнить производительность, качество композиции, удобство API и эксплуатационные риски двух стеков без принятия преждевременного решения по core dependency. citeturn26search5turn37view3turn37view0turn37view1

**Отложить.** Полноценную интеграцию Tiled/LDtk/Aseprite в production-chain лучше отложить до тех пор, пока не стабилизируется ваш внутренний IR. ## Non-goals

На этом этапе не нужно делать LLM-driven visual runtime, provider/runtime calls, network generation или “умный Unity-side assembly”. Ваши документы уже жёстко фиксируют, что Runtime/Unity должны оставаться свободными от LLM/media provider calls, а редакторный pipeline должен работать через deterministic safe fallbacks, quarantine и reviewed promotion. Значит, любые идеи вроде runtime recomposition через внешнего провайдера или prompt-derived authoritative state надо считать architectural regressions. citeturn41view1turn41view3

Также сейчас не нужно пытаться решить “финальное коммерческое качество арта”. Ваш roadmap правильно отделяет доказательство deterministic layer ordering/palette slots/atlas metadata от production art. На этой стадии главное — **контракт, воспроизводимость, масштабирование и reviewability**, а не художественная полировка. Внешние примеры вроде LPC generator и Aavegotchi показывают, что сначала побеждает структура данных и совместимость деталей, а не визуальный максимализм каждой отдельной картинки. citeturn41view1turn17view0turn17view1

И наконец, не стоит раньше времени расширять public GamePackage schema под сырой visual pipeline. Сейчас лучше держать synthesis IR и materialization IR в sidecar/editor namespace, а в основной package поднимать только те сущности, которые реально доказали свою полезность для consumer-side и review/export flows. Это прямо совпадает с внутренними ограничениями по schema mutation и consumer proof. citeturn41view1
